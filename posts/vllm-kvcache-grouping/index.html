vLLM 中的几种 KVCache 分组机制

整理了 vLLM 在混合 Attention 模型下几种 KVCache 分组方式，以及 HMA 为什么存在、解决了什么问题。

2026-06-09 vLLM Inference

KVCache 的分组是 HMA 中非常重要的部分，HMA 是为了解决在混合 Attention 模型下的 KVCache 高效管理诞生的技术。其核心在于，通过分组实现两种 Attention 类型对应的 KVCache 共享同一块 Buffer。

首先统一语言，这一节中，KVCache 类型指不同的 KVCacheSpec，大小指一个 block 占的物理内存字节数，通常为：

block_size * num_head * head_dim * sizeof(cache_dtype)

统一的 KVCacheSpec 组

每个 Attention 层的 KVCache 完全一致。这里的完全一致是指类型一致、大小一致。这是最广泛、最基础的 KVCache 组，几乎所有的非混合 Attention 模型都属于这一类，典型模型如 Qwen2.5、DeepSeek V3.1 等。

这种组中，每一个 attention 层都有一块 kvcache buffer，每个 buffer 上都有 num_gpu_blocks 个 blocks，由 KVCacheManager 统一从 BlockPool 调度即可。

类型统一的 KVCacheSpec 组

不同 Attention 层，KVCache type 相同，但大小不一样。典型模型有 DeepSeek-V3.2、minicpm 4.1，以及 spec decode 或 MTP 层中的 kv head 数量和主模型不一致的场景。

特性 PR：https://github.com/vllm-project/vllm/pull/25101

这种组中，同样是每一个 attention 层都有一块 kvcache buffer，每个 buffer 上都有 num_gpu_blocks 个 blocks，只是每层的 buffer 大小不一致。因此在这种分组策略下，同一个 token 在不同层上分配的 block id 仍然是相同的。

混合 KVCacheSpec 组

不同 Attention 层，KVCache type 不同，大小也不一定一样。典型模型有 Gemma3、Qwen3-Next、Qwen3.5 等。

这里就是 HMA 的核心内容了。

首先理解为什么有这个问题

让我们站在 Qwen3-Next 还没有 HMA 的时间点上，此时 vLLM 的行为是：给每层分配同样大小的一块 buffer。结合 linear attention 和 full attention 的 kvcache 差异，可以看到这里有明显浪费。对于 linear attention 层来说，每个请求需要的 kvcache 总大小是固定的，只需要固定 N 个 block（N = 1），但系统仍然强行给它分配 NUM_BLOCKS 个 block。

而在 Qwen3-Next 中，linear attention 层实际上比 full attention 层还要多两倍，这会进一步放大浪费。

UniformKVCacheSpecs 方案分析

UniformKVCacheSpecs 的思路乍看很自然：既然某些层需要的 kvcache 更小，那就按需给每层分配不同大小的 kvcache。

问题在于，这个机制实际上仍要求每一层的 block 数量相等。因为 vLLM 的 KVCacheCoordinator 中只有一个 block pool，而且当只有一组 kvcache 时，也只有一个 SingleTypeKVCacheManager。这意味着对于一个请求来说，在每一层分配的 block id 是相同的，因此我们想要的“只给 linear attention 层分配一个 block”并不能直接做到。

理论上可以通过多 block pool 解决，但这样不仅会带来架构改动，还会引入 prefix cache 场景下 block 预留数量不可预估的问题。保守预留的话，最后又会退化成每层 block 数相同的设计。所以 UniformKVCacheSpecs 并不能很好地解决 hybrid model 中 KVCache 浪费的问题。

HMA

首先建立整体认知：HMA 的核心是不同层去共享同一块 buffer、一个 block pool 和一份 block table，从而减少 KVCache 的浪费与碎片化。

下图以 Qwen3-Next 为例，直观感受一下 HMA 的样子。普通 full attention 和 linear attention 的层数比例为 1:3，因此 shared_by 中，一层 full attention 层和三层 linear attention 层共享同一块 buffer。达成的效果是：对于一个 token，每个 KVCacheTensor 上会分配四个 block id，shared by 中的各层每层一个。

Hybrid models as first class citizens in vLLM

HMA 中最重要的两点：

  1. 不同类型的 KVCacheSpec 的 page size，也就是一个 block 的物理内存大小，需要对齐。vLLM 当前主要有两种对齐方式：放大 block size 到原来的 x 倍，或者添加一个 pad。
  2. 不同类型的 kvcache 虽然共享同一个 buffer，但都拥有自己独立的一份内存视图。也就是说，物理内存是同一片，但对物理内存的解读方式不同。

HMA 为了兼容更多 attention backend，还做了一个关键工作：将算子支持的 block size 与 KVCacheSpec 的 page size 解耦。具体来说，attention 算子接收到的 block size、block table、slot mapping 等，都是基于算子支持的 block size 计算的；而调度侧仍通过更大的 block size 完成 block 分配。可以把它理解为，调度侧一次性分配了 x 个 kernel 侧的 blocks。这使得更多 attention backend 可以使用 HMA。
